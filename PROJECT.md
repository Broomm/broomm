# Broomm product specification

## Purpose

Broomm provides a console-like experience for browsing, installing, and playing games from a user's RomM catalogue. The application is native Flutter and targets Windows, macOS, Linux, and Android. Initial development and hands-on verification focus on macOS and Linux. Windows and Android remain product targets, with an intentionally simpler emulator handoff on Android.

The UI is heavily inspired by the PS5 home screen and Store: a prominent horizontal game/app row, a focused selection, rich game artwork, clear primary actions, and a consistent controller navigation model. Use Broomm branding and original interface assets.

Use the existing mint infinity mark as Broomm's application icon on Windows,
macOS, Linux and Android, in every build mode. Preserve the dark teal treatment
and the mark's proportions. Provide native sizes and Android adaptive/themed
variants; keep the checked-in artwork and reproducible rendering recipe together.

## Home and Store

- A new library has three persistent apps: **Broomm settings**, **Game Store**, and **Emulator Settings**. Profile selection and connection setup are supporting flows, rather than extra home apps. Emulator Settings provides managed installation/configuration; implemented host/build combinations are recorded in IMPLEMENTATION.md. Downloads and an available application update add conditional Home entries.
- The Store browses the connected RomM catalogue, with artwork, game details, search, and platform/category browsing. Related ROM versions appear as one game entry using RomM's metadata grouping. Before downloading a grouped game, let the user choose the release using its filename/region/revision tags. Preserve the selected ROM's identity and permission checks. It provides installation actions for that catalogue; purchases and a separate commercial marketplace are outside this specification.
- A game appears as playable on Home only after its installation succeeds. Partial downloads must not become playable entries. Downloads form a persistent queue, with a configurable maximum of 1–6 simultaneous game transfers (default 3) and a Downloads app beside Game Store while active, queued or failed entries exist. Each job has independent progress, cancellation, retries and removal. Separate private transfer stages can overlap; shared library publication and emulator content mutations remain serialized and OS-locked. Removing a failed download discards its partial payload and selected artwork, preserving any already completed base game and all progress. Do not display a persistent transfer overlay. Always validate complete transfer sizes; an optional full game-checksum scan is off by default. This setting does not weaken firmware, add-on, save or executable validation.
- Installed games appear on Home like console games, with a clear Play action and relevant installation or synchronization status.
- Official Broomm releases check `Broomm/broomm` on GitHub at startup and every six hours. When a newer release has a complete package for this host, show **Update Broomm** first on Home while preserving the current selection. Activating it starts a controller-navigable download, integrity check, installation and desktop restart. Settings provides a manual check and Stable / Release candidates / Match installed release channels; the default follows the installed release. Do not install without activating the update action, offer downgrades, or automatically replace development/PR builds. Preserve all game, emulator, account and progress data. Finish/checkpoint active work before exit, refuse unsafe/read-only installation layouts, retain the previous desktop bundle for recovery and never overwrite a foreign destination. Failed preparation must allow retry and identify its phase, with redacted operational diagnostics. Android uses its user-confirmed system package installer and retained signing identity. This application-update feature does not change the manual/setup-JSON policy for emulator updates.
- When a download is queued with a SteamGridDB mapping, immediately offer sequential controller-navigable artwork pickers while transfer continues: square PNG grids for the Home tile, heroes for the background, then an optional game logo. Show image dimensions. Persist choices independently of payload transfer. A selected logo replaces the large typed Home title; keep the text as the missing/invalid/disabled-artwork fallback and accessible name. Skipping, missing artwork or a provider failure must not discard a game or existing selection. SteamGridDB uses a separately configured secure API key; do not expose or repurpose RomM credentials.
- Horizontal Home navigation keeps the selected tile near the center within a small stationary zone, bounded by the ends of the rail. Controller text entry uses a Steam-inspired keyboard docked inside the existing window, editing the original input. Provide visible controller shortcuts: Y inserts a space, X deletes backward, holding L2 applies Shift across typed characters, R2 submits, L3 toggles Caps Lock and L1/R1 move the caret. Start remains a submit shortcut. These actions apply only to the active dock; releases, disconnection and loss of app focus must not leave Shift stuck or edit a covered field. Pointer activation types inline; keyboard navigation requires Enter to edit and Escape returns to navigation with focus retained. Do not open a separate keyboard dialog or duplicate the input.
- A selected/hovered Home game shows its hero top aligned over the existing background, covering 75% of the screen height with aspect-preserving cover/zoom and a transparent bottom fade. Keep the current background visible through the fade and below the image. Without selected artwork, retain the cropped-poster tile and existing background.
- Home has larger square app/game icons without visible names underneath; retain the prominent selected title/logo and accessible icon labels. Play and Options sit beside each other. Remove the top-left brand header and place the profile and tagline at the bottom right, with reachable Home/profile navigation. Notifications appear as readable top-left cards and expire without moving content or stealing focus. Active transfer progress/cancellation remains available until completion; failures also retain their owning operation's state.
- Select on a selected/hovered Home game opens a menu with **Select Artwork** and **Delete**, plus **Download Updates and DLC** for implemented integrations. Provide keyboard, pointer and touch alternatives. Artwork selection repeats the same workflow using the current RomM mapping. Confirmed Delete removes shared local game files, installed updates/DLC and selected artwork for that server across profiles, preserving every profile's saves/states and all remote RomM content. Native content still used by another installed version is retained. Interrupted cleanup must remain identifiable and retryable.
- Removing an installed game must distinguish local game content from saved progress. Uninstalling content does not silently delete any profile's saves or remote RomM files.
- Catalogue failures and lost connectivity must be visible without turning an installed library into an apparently empty one.
- First use asks for a server address, verifies RomM compatibility, then signs in to an account before opening Home. Subsequent launches retain the server-first, server-scoped profile chooser. Home uses a horizontal row of large app tiles, a focused selection and a prominent description/action; the Store has collection picks, cover art, game details, platform filtering and server-side search.
- Every flow, including server/login text entry, filtering, settings and error recovery, must work with controller focus and an on-screen keyboard. Controller activation opens that keyboard. Pointer/touch selection starts inline editing. Keyboard navigation focuses a read-only field; Enter starts inline editing and Escape ends it while retaining navigation focus. Changing input devices must work within the same session.
- Directional navigation follows rows and columns, keeps the selected control visible and stops at their edges. Home's primary action returns to its selected tile. Returning from a dialog restores its invoking control; completed background work must not steal newer focus. Screen, focus and scrolling motion respects both the saved reduced-motion preference and the platform accessibility setting.
- Focusing a scroll view's first or last control row reveals its beginning or end, including headings and trailing content. Focused cards remain fully visible when they fit; when a card or surrounding content exceeds the viewport, keep the active control visible. Arrow/controller directions follow the rendered arrangement, including buttons that wrap onto separate rows in smaller windows.
- Show transfer progress, cancellation, failures and completion. Cancellation/retry may restart the transfer; never expose partial content as a completed game. Completed downloads offer Play for implemented platform/build integrations; other platforms remain browsable and downloadable without claiming launch support.

## Profiles and shared installations

Each Broomm profile represents an account on a saved RomM server. Broomm remembers multiple servers, but only one server can be active at a time. Users select a server first, then choose one of the profiles known for that server or add a profile. Use the server-scoped profile selection, explicit activation, and focus behavior in Teddy as the reference; see the [profile flow](docs/profiles-and-servers.md).

Profiles share the installed ROM/game files. Saves, save states, and other writable game data are separate. Authentication and profile preferences are account-scoped; emulator configuration stays within Broomm's own storage. Account identity includes the server as well as its user identity; matching usernames or remote numeric IDs on different servers do not merge profiles.

Remember reusable authentication in the platform secure store, independently for each server/account. Never persist the password or OAuth access token in settings. Choosing a known profile restores its refresh token or client token without another password while RomM still accepts it. Profile switching retains that credential; explicit device sign-out removes it without deleting profile metadata or progress. Storage/network failures remain visible and do not masquerade as a missing account. Startup still requires explicit server/profile selection.

API key pairing accepts RomM's eight-character alphanumeric code. Normalize lowercase and hyphens as RomM 5.4.0 does; never restrict pairing entry to a numeric keypad. The returned token still requires authenticated account verification before profile association.

Switching servers or profiles must not redirect progress or pending uploads to a different account. Inactive servers retain their saved profiles, installations, and pending progress. Only the selected server/account supplies the current catalogue and authenticated work. Locally available games and progress remain usable offline for a known profile; connectivity failure must not erase them. Online permission revocation is distinct from being offline; shared local content does not override RomM catalogue permissions.

The initial RomM integration target is **5.4.0**, with the owner's instance at `https://romm.docubi.casa`. Support for older releases is outside the initial target.

## Installation and emulator setup

Broomm provisions managed emulator installations shared across its profiles. Users can instead select an existing system-wide executable for a platform. On desktop, **all configuration used for a Broomm session remains local to Broomm in either case**. Never change a system-wide installation's configuration, user profile, libraries, or executable. An adapter must supply a verified Broomm-local configuration/data root before it can support that executable.

Automatic provisioning is driven by **setup JSON files**, following PGCS's manifest-based model. Emulator updates are never automatic. Users update a managed emulator manually, or explicitly obtain a newer `setup.json` from Broomm and import/install it through the app. Broomm reads that file and performs the requested installation/update. Selecting an existing system executable does not authorize updating it.

Bundle usable delivery recipes with the application, independently of a developer checkout. Normal supported setup must complete inside Broomm without asking users to obtain an external pack or import a setup JSON. Download available, reviewed emulator/core versions after explicit setup confirmation. Keep optional custom/offline imports for users who choose them. Verify archive and resulting application identities before publishing a managed installation. Unavailable reviewed builds must be reported rather than silently replaced with an unverified rolling version. Retain usable installed cores until explicit setup, preserve ordinary saves, and isolate incompatible save-state builds in both storage and synchronization.

Emulator Settings lists every platform reported by the active RomM server, with supported emulator cards beneath each platform and an explanatory empty state where none is supported. Only configured emulators can be defaults; a platform with none configured has no default. Successful setup makes that emulator the default, including when another emulator was already configured. Users can subsequently select another configured alternative. Home Play uses that choice. Setup review and confirmation expand inside the selected card. Configured cards also offer confirmed removal of the shared managed application and installation resources, preserving all profile configuration, saves/states and shared game files. Removal explains effects on other platforms sharing the same emulator and cannot run during a game.

Give the default emulator card a green outline. Configured cards offer **Open emulator**, without a game, for changing this profile's private Broomm settings. Hand the application to the OS and leave Broomm visible and navigable. Do not treat it as a game session, watch its lifetime, wait for its exit, restore focus on exit or require it to close before quitting Broomm. Keep the same profile-local data as gameplay and passive native file locks protecting concurrent writes. On macOS, launch complete app bundles through Launch Services, including Azahar; the private portable melonDS executable uses a detached launch. Do not run controller preparation or change system installation preferences for this action.

The initial emulator roster is the concrete PGCS roster: RetroArch, PCSX2, ARMSX2, Dolphin, DuckStation, RPCS3, PPSSPP, Vita3K, xemu, melonDS, Azahar, Cemu, and Ryubing. The owner additionally selected **Eden** as a Nintendo Switch alternative, **Astris for macOS** and **Citra MMJ for Android**. See the [emulator inventory](docs/emulator-support.md) for systems and host distinctions. Tight support for this small set takes priority over a general-purpose emulator framework.

PlayStation uses DuckStation with profile/game-private whole memory cards. PlayStation 2 offers PCSX2 and ARMSX2 where supported by the host/build; both use the same ordinary memory cards for a given profile/game, with separate emulator settings and build-specific save states. Missing BIOS images can be obtained from that platform's RomM firmware catalogue, preserving existing private firmware. Normal native settings remain within Broomm. Alternate executables must not cause progress to cross profile boundaries or make incompatible save states appear interchangeable.

PSP uses PPSSPP with a profile-private memory stick, one PSP controller and the normal loading/pairing/menu/disconnect flow. Native savedata directories travel as ZIPs, preserving their console files and excluding Broomm-owned static DLC. Save states require the same executable, game revision and host compatibility group. Native ISO, CSO and PBP identities must be verified rather than inferred from filenames. PSP content in RomM must identify its native `PSP/GAME` or `PSP/SAVEDATA` destination, directly or inside a ZIP; game-specific update execution is distinct from installing those files.

Switch alternatives retain separate private emulator configuration, console accounts and installed-content records. Ordinary cloud exports use the same logical save/device format, so changing the default does not create a separate cloud history. Preserve native account identities; map the game's files into the selected console's existing save boundary. Prepare known installed updates/DLC for a newly selected default before launching. Eden consumes native NAND content rather than Ryubing selection JSON. State support and build/host verification remain specific to each backend; an upstream experimental build is not a compatibility guarantee.

The RetroArch console routes use pinned cores selected per platform, with each profile/game/core's writable data kept separate. Save states require matching frontend/core builds. Special peripherals and arcade ROMset dependencies need explicit coverage; sharing a frontend is not evidence that every core or game is supported.

RetroArch progress integration must follow the pinned frontend/core's observed native filenames and option precedence. Dreamcast VMUs are private per game on every controller port; shared system VMUs are not an acceptable automatic cloud boundary. Preserve legacy cards during migration and do not guess ownership when several historical games could share them. Platforms/cores without an ordinary cartridge-save interface can retain matched save-state support, with that limitation stated explicitly.

PS4 has no built-in emulator or shadPS4 recipe for now. It remains normally browsable and downloadable, with no platform-specific restrictions added. A generic user-defined emulator setup JSON facility is a future extension beyond the current pinned-roster importer.

On macOS, PS3 also offers the Intel RPCS3 distribution as a separate selectable emulator, including execution through an already installed Rosetta on Apple Silicon. It can be set as the platform default independently of the native ARM distribution. Both use the profile's Broomm-owned ordinary PS3 data, firmware, updates and DLC; retain separate executable releases and architecture-specific compilation caches. Broomm must not install Rosetta or change a system RPCS3 installation. The alternative enables owner compatibility testing; improved compatibility or performance is not presumed.

Downloading a supported game also discovers, downloads and installs its updates and DLC from RomM's game-file manifest. Recognize `updates/`, `update/` and `dlc/`, including their API content categories. Start with Nintendo 3DS/Azahar and decrypted, unpacked CIA packages. Verify that packages match the base title/region. **Download Updates and DLC** refreshes an installed game's manifest and reconciles differences without downloading the base game again. Repeat checks avoid unnecessary transfers/imports and repair damaged Broomm-owned installed content. Keep the completed base game and progress if add-on work fails, and show a retry action. Apply shared content to each account's private emulator storage before gameplay; keep saves and states private. Do not launch the game while its installation is being applied. Other emulator/host integrations require their own validated import adapters.

Wii/Dolphin package support includes WAD game channels, channel updates and DLC, with owned ticket/content cleanup and retained base/DLC progress. Exclude system/IOS WADs. Switch/Ryubing support includes NSP updates/DLC selected from native content metadata. Before first use, missing Switch resources can be installed from exactly one firmware ZIP, `prod.keys`, and `title.keys` in that platform's RomM firmware catalogue. Validate them, preserve configured resources and retain packages still referenced by another installed game/profile. Emulator and firmware updates remain user-initiated.

Required firmware, BIOS, keys, and emulator-specific setup must be explained in the product. If a PS3 launch lacks configured firmware, automatically look in the active RomM platform's BIOS/firmware catalogue, download a uniquely identified PUP, verify its checksum, and install it into Broomm-managed storage. Reuse installed firmware across private profiles without changing system installations. Explain missing, ambiguous or unusable resources. This authorization does not extend to fetching keys or firmware from unrelated services. Existing user configuration and saves must be preserved.

PS3 also supports the update/DLC workflow using region/title-matching PKG packages and associated user-provided RAP files. Install privately, reconcile differences from RomM, and remove owned native content when deleting a game while preserving savedata and content still used by another installation. Support extracted PS3 games and ISO images. Download an encrypted ISO's adjacent `.dkey` with the game, retain its matching stem and directory, and let RPCS3 consume the sidecar through its native ISO reader. Do not put key contents in arguments, logs or shared configuration. Nintendo DS uses melonDS and supports importing ordinary raw DS save files for cloud-save testing.

RPCS3 package ownership applies to individual package files: a title directory can also contain files created by the game. Preserve those files during add-on install, repair and removal. Retain pre-existing overlapping files before replacing them, and restore them when Broomm's last package owner is removed. An independently running Broomm instance keeps its download lock; other instances should still display the persisted queue read-only and offer refresh/recovery after the writer exits.

## Starting and controlling a game

On desktop, before gameplay, show a controller setup screen that lets users assign connected controllers to player 1, player 2, and further supported ports. While the emulator initializes, show an explicit loading screen. Only show pairing slots and detected controllers once initialization is complete and players can actually join; a disabled or empty pairing screen must not stand in for loading. The screen must show what the chosen emulator can actually apply, identify ambiguity, and allow a controller test. Player slots reflect the selected emulator/system's real limits.

The original Flutter prototype uses the six supplied test ROMs as a static library. The application also launches completed RomM downloads, with a platform-specific entry-file chooser when necessary. On desktop, **R3 + Select/Back** opens a paused-game menu with **Controller pairing** as its initial single option. It reuses the pre-game pairing screen, applies player/controller changes without restarting, and automatically reopens pairing when an assigned controller disconnects. At least one connected player is required to begin or resume. Retain the local controller lab as a separate diagnostic route.

The pairing screen uses large live diagrams of the target platform's controller, illuminating the controls to which the joined source is mapped. L1 + R1 joins; after joining it cycles controller types on systems with multiple types (currently Wii). L3 + R1 swaps both A/B and X/Y together, independently of controller type. L3 + R2 toggles gyro for the joined player, including during gameplay, without disabling accelerometer input. Upright Remote and Remote + Nunchuk use relative right-stick pointing when gyro pointing is disabled or the source lacks the necessary sensors. Broomm guesses the initial orientation from the source controller family. Holding Select removes a controller; holding Start applies/starts or resumes. Short button presses, including Start/Select, remain available for testing. Initially show only Player 1; each join adds its tester and the next join card, bounded by the platform's player limit. Wii supports upright Remote, Classic, Remote + Nunchuk and horizontal Remote with one large active tester, all four illustrated choices along the bottom, and live configuration changes. Supported source controllers also provide accelerometer/gyro input to motion-capable targets, scoped by what the emulator runtime actually exposes. Motion follows player assignment independently of face orientation and becomes neutral during pairing, disconnection or failed readings.

The pairing UI must stay responsive during emulator output and live controller updates. Hide motion bars when gyro is inactive, including disabled, unavailable or unreadable gyro and target types that do not use it. Accelerometer routing remains independent of that display rule.

The desktop prototype keeps ordinary window decorations and the user's chosen window size across its screens. Returning from gameplay must restore Broomm after either normal emulator exit or failure. Unknown controller/pause state must remain visible and recoverable. Console controller sockets must reflect paired players; exposing stable host input routes must not create extra connected players in a game.

For supported pinned RPCS3 builds, show the native loading dialog's file/module counters and current-phase progress in Broomm. Use an indeterminate bar when counters are absent or between phases; readiness still requires the existing input/pause acknowledgment. Do not capture emulator windows: the owner canceled the live-preview direction. Preserve the owner's RPCS3 performance settings.

Joining, leaving, reordering players, choosing layout/presets, confirming, cancelling, and resolving routine errors must work with a controller. Device disconnects and reconnects need understandable feedback. An assignment shown as confirmed must correspond to the input route the emulator will consume.

A central desktop launch flow is **Steam → Broomm → emulator**, with both gameplay and Broomm settings/controller pairing available to the player. Support Steam Big Picture on desktop and gamescope-based Steam Gaming Mode, including Bazzite's handheld/HTPC edition. The settings/pairing goal is a menu over the emulator's game presentation without manual desktop window management. A separate-window macOS prototype does not establish that integration.

The whole Broomm interface must be navigable with a controller, comparable to Steam Big Picture. This includes Home, Store, Settings, profiles, installation progress, launch preparation, and conflict resolution. Text entry needs an accessible on-screen or platform keyboard route. Keyboard, mouse, and Android touch remain supported inputs.

Broomm permits **only one active game session at a time**, including across app instances sharing its data. Starting another game requires the previous session's writer to stop. Server/profile changes cannot change a running session's ownership; the initial UI keeps those changes unavailable until the session ends. Pending uploads may outlive that session and retain their original owner.

## Android handoff

Android detects and uses compatible installed emulator apps and can guide users through installing an emulator when absent. It launches the selected emulator with the ROM and the profile's save/save-state inputs through that emulator's supported contract. It does not run the desktop controller join/assignment machinery, inject bridges, render in-game Broomm overlays, or attempt desktop-style sandboxing of the emulator app.

Use the installed emulator's ordinary Android behavior. Game selection, local progress, and RomM sync remain Broomm responsibilities, but private save-folder access and launch parameters must be verified per emulator. Where Android cannot redirect or access saves/states, show the precise limitation rather than claim a successful handoff or overwrite another profile's progress. This platform-specific scope is an explicit exception to desktop configuration isolation.

For Citra MMJ, assume shared `citra-emu` storage and request a persistent folder grant. Warn that private `Android/data` / Storage Access builds are unsupported, and reject a folder outside this shared-root contract. Keep profile progress separately in Broomm, copy the active game's saves into MMJ's required paths only while it is closed, and preserve/restore existing standalone MMJ progress. Do not assume that selecting a folder proves MMJ is configured to consume it. An interrupted or uncertain swap must retain recovery copies and offer an explicit way to finish without overwriting the shared folder.

Installation uses user-confirmed app/store or APK installer actions and subsequent package inspection; opening an installer is not confirmation of installation. Data-folder grants retain profile identity. Returning to Broomm does not establish emulator shutdown: require suitable writer-exit evidence or explicit closure confirmation before save capture/restore, retain interrupted-session recovery and never silently apply desktop installers on Android. The [Android audit](docs/android-emulators.md) records the current partial implementation. Cloud save/state and update/DLC parity remain product requirements.

For the current Android milestone, Install downloads the official compatible APK
and opens Android's confirmation flow, with store-only/paid exceptions explained.
Detect ARMSX2 stable `com.armsx2` and nightly `com.armsx2.nightly`, preferring
enabled stable when both exist. Connect a stable emulator/package folder once
for all Broomm profiles; keep per-profile/game progress privately and preserve
standalone saves through journaled swaps. On return, show **Finished? Sync
progress** and explain that the player must save/close the emulator first.
The owner's explicit confirmation is sufficient; do not add process-exit hooks
or OS probing. Broomm's own transfer/session locks still apply. BIOS/firmware
and new content installers are later work. No additional Wii update support is
required for the owner's library; preserve existing desktop WAD/DLC behavior.

## Progress across devices

Broomm automatically synchronizes in-game saves and supported save states with the active profile's RomM account so play can continue on another device. Pull current progress before starting a connected session, preserve local changes, and upload completed progress when it is safe to do so. Failed transfers remain visible and retryable.

Maintain a `BROOMM` save slot per game and RomM account in Broomm's emulator namespace. Append versions named `Broomm [yyyy-mm-dd_hh-mm-ss]` with the correct native extension: ordinary DS saves remain raw `.sav`, SNES SRAM remains `.srm`, and directory/multifile exports use `.zip`. Let RomM assign the timestamp before the extension, following its autosave format. Automatically synchronize only the latest version in this slot; preserve earlier versions and unrelated slots. New writes must not overwrite the old unslotted `broomm` asset; it may be read once for migration when no BROOMM history exists.

The game's Select/Options menu provides **Use existing save file**, which explicitly copies a selected account-owned RomM save into local working progress and a new BROOMM version while leaving its source unchanged, and **Backup savefile**, which explicitly creates an independent remote save under a user-supplied name with the appropriate extension without replacing an existing filename. Backups never become automatic synchronization targets. Keep state compatibility/provenance separate from ordinary native save bytes; a native `.sav` must not conceal a compressed Broomm bundle. Matching state archives may accompany a version through RomM's state assets.

Offline play retains progress locally. When the originating server/account is active and connectivity returns, compare the remote save's hash with the last acknowledged common baseline. If the remote hash still matches that baseline, upload the new local progress without a conflict prompt. If local and remote have both changed and differ, notify the user and let them choose which to keep, preserving both until resolution succeeds. Equal local/remote content needs no prompt; a remote-only change can be downloaded safely. Apply the same ownership and conflict rules to supported states.

A lost network connection, revoked login, app crash, or interrupted transfer must not discard progress. Show whether progress is synchronized, local-only, pending, conflicted, or incompatible with the chosen emulator. Unknown remote state is not a hash mismatch and does not authorize overwriting either copy.

Do not checksum ROM contents during launch or ordinary cloud-save discovery. Use the installed game's server/ROM/file identity and publication receipt, plus emulator-confirmed native title identity where needed. Installation/download verification is a separate operation; save-content hashes still establish synchronization and conflicts.

Launch preparation must remain cancellable. Quit must acknowledge the request promptly, show the phase being stopped and offer a visible way to leave if graceful shutdown stalls. Retain unfinished progress and recovery records. A surviving emulator must keep writer exclusion until its exit is confirmed; any force-quit recovery action requires explicit confirmation and verified process identity, never a PID alone or deletion of a live lock.

Initialize cloud synchronization automatically after installation and profile activation, including existing installed games without a first-sync record. Verify the current account's managed remote history before acknowledging an empty save. Restore existing BROOMM progress automatically when the device has no progress, and retain the normal conflict rules when both sides have progress. A missing emulator or an unresolved native save identity can defer initialization until the adapter is ready; it must never produce a false successful sync. Do not require the user to open a cloud menu or create a dummy remote save to initialize an empty game.

Each Home game tile has a top-right cloud-status badge for the active profile: green cloud/check for the last confirmed sync, amber cloud/sync while waiting to sync, and red cloud/off when attention is needed (including conflicts or damaged/interrupted recovery). A badge is a cached observation of durable sync state, not a claim of continuous remote freshness. Tooltips and accessible labels explain its state. Badge rendering must not prepare emulators or scan save payloads.

Save states depend on the emulator, core, build, game revision, and sometimes host architecture. Synchronizing a state file does not guarantee another emulator or device can load it. Broomm must explain incompatibility and keep ordinary game saves separate from state snapshots. Some emulators do not support usable states at all; that limitation must be shown for that integration.

## In-game settings ambition

Investigate a controller-operated Broomm menu accessible while playing, especially for emulators without a suitable full-screen settings experience. Desired actions include controller setup and render-resolution changes, alongside Broomm session/settings actions.

Use tight, emulator-specific integration and prefer DLL/shared-library injection and similar external techniques over modifying or forking emulators. Working controller injection, overlay rendering, and settings control must each be proven for the selected builds. Android is excluded from this work.

Broomm knows which supported settings require restart. It tells the user when a changed setting requires restart and applies the appropriate behavior; live changes do not receive a generic restart warning. Unknown behavior is an unfinished integration to investigate, not a reason to warn indiscriminately. Some controls may be unavailable until their adapter is complete; opening a native UI is a fallback where useful, not the intended replacement for the unified menu.

## Related applications and shared contracts

The native Nintendo Switch companion is maintained separately in [broomm-nsw](../broomm-nsw/PROJECT.md). Its requirements, implementation, dependencies and console-specific decisions belong there. General Broomm decisions and the Flutter application's implementation remain in this project, including Switch emulation. The applications share the RomM account-isolation, native-save archive and version/conflict contracts documented here; changes to those shared contracts must remain compatible across clients. The companion does not change the Flutter application's platform scope or Dart workflow requirement.

## Later scope

- **Computer games:** later support RomM's PC-game content, including native execution and appropriate compatibility tools. Windows games on Linux should select a compatible Proton-based route automatically, with explicit overrides and honest per-title compatibility status.
- **RetroAchievements:** feasible integration direction, deferred. No achievement login, unlocking engine, or achievement overlay is required for the initial release.

The initial implementation focuses on emulated games. Desktop overlay research can proceed as a bounded experiment without making it a prerequisite for every launch. PGCS's cartridge management, Steam shortcut synchronization, daemon, and historical emulator queue are outside Broomm's product requirements.

## Implementation and development constraints

GitHub builds/releases follow the owner's Teddy reference: `version.txt` selects
major/minor, successful `main`/`develop` publication automatically advances stable
patch / release-candidate tags, and PRs build without publishing. Keep the same
five package targets (macOS universal, Windows x64, Linux x64/ARM64, Android
universal). Build coverage does not replace native emulator acceptance. See the
[release contract and repository setup](docs/github-releases.md).

Application workflows live in Dart within the Flutter application. Do not import PGCS code or introduce Go code/helpers. PGCS is a reference for engineering practices, emulator knowledge, manifests, and behavior. Optional injection bridges may be implemented in C and bundled as precompiled, host/architecture-specific libraries after validation.

Devbox manages project dependencies. Pre-provisioned Xcode/Apple SDK and Windows C++/Windows SDK build hosts are approved; this does not authorize installing new OS dependencies as part of project bootstrap.
