# Downloads, keyboard and additional emulator progress

This follow-up implements the owner's queue/UI, melonDS, PS3 resources/add-ons and remaining playable-system save requests. It extends the earlier [managed cloud-save contract](cloud-saves.md); its `broomm` ownership, offline/conflict handling and explicit import/backup rules remain in force. See [machine-readable evidence](library-and-progress-followup.json) for final commands, hashes and scoped results. Earlier milestone counts remain historical.

## Library and text entry

Home's horizontal rail uses an 18% center zone. A visible selection outside that zone scrolls toward the middle; either end still clamps to the available content. Store Search uses the same padding as the adjacent actions.

Downloads are serial, account-scoped and checkpointed before external effects. A Downloads app appears between Store and Emulator Settings while entries remain. Its screen orders the active transfer, queued games, then failed entries, with cancel/retry/remove actions. Restarted unfinished entries require an explicit retry, rather than silently resuming installation. Cancelled/failed private base-transfer stages are disposed; verified base games survive a later add-on failure. Removing an unsuccessful transfer discards its chosen artwork, without deleting a verified base game or saves. Active game sessions defer the add-on mutation phase until the emulator exits.

Queue records live at `downloads/<server>/<profile>/queue.json`, protected by a stable OS queue lock. No credentials are serialized. Artwork is offered on enqueue, including a metadata-refresh fallback for lightweight catalogue records, and transfer continues beneath the picker. Choices live in `home-artwork/<server>/<rom>/`, published under a separate stable artwork lock. This avoids a completed game's artwork update contending with the next game's transfer lock. Legacy artwork inside installed game directories remains readable. Cleanup rejects unrelated files and links. Each candidate displays its pixel width and height.

`ConsoleKeyboardHost` docks the Steam-inspired keyboard below the existing Navigator, shrinking its viewport and revealing the original field. There is one TextField, retaining its cursor, selection and password visibility. Physical keyboard/pointer entry stays inline. Controller acceptance opens the dock; Back closes it without submitting or discarding edits; Enter/Done submits. X deletes backward while the dock is open. Shift/Caps, punctuation, selection replacement, Unicode-aware deletion/caret movement, explicit Paste, and an empty emoji position are included. Closing a route disposes its keyboard safely. This does not create another native window.

## Nintendo DS / melonDS

The user-selected roster already includes melonDS. The managed pack now includes the official [melonDS 1.1 universal macOS release](https://github.com/melonDS-emu/melonDS/releases/tag/1.1), with inventory/symbol assets and the existing installation confirmation workflow. No new Dart package, SDL runtime or OS dependency was added. The application is GPLv3; obtain source and license through that release. SDL/Qt are part of the upstream static executable, not new runtimes loaded by Broomm.

The tested executable SHA-256 is `b76167f554bb6b50a712cbf025c6872159318afb12d840fadc885785f6bc35c4`. Its Qt/macOS preferences do not follow a child HOME override reliably. Therefore each Broomm profile uses a verified private executable anchor beside its own `portable/` directory, leaving both the shared managed source and any system emulator untouched. Launch revalidates the pinned executable. Broomm writes only its joystick/save/state paths and seed defaults, preserving other native TOML settings. Built-in DS BIOS/direct boot is used; no BIOS download is needed for this mode.

ROM header game code plus revision identifies ordinary saves, independently of the filename. The adapter's private saves and states use that identity. Cloud format `melonds-sav-v1` stores ordinary SRAM as `save/game.sav` and uses the existing build/host state groups. Explicit import accepts one raw `.sav` at a recognized EEPROM/flash size (512 B; 8, 64, 128, 256, 512 KiB; 1 or 8 MiB), or a bounded ZIP containing one such save. DeSmuME DSV containers and ambiguous multi-file archives are refused. Actual game compatibility and state loading still require gameplay acceptance.

The injected bridge resolves the exact executable's SDL2 DynAPI table and samples controllers in that same runtime. Its table validation uses public stubs that survive upstream LTO; it rejects missing required functions before sampling. Logical port 1 opens its selected actual SDL instance. Pause/resume uses the pinned Qt MainWindow/EmuThread path, validated arm64 instruction patterns, offsets and native readback. A real supplied Pokémon Black ROM reached native pause, pairing, resume, live face swap and normal exit. This uses synthetic devices inside the actual emulator runtime; physical-controller gameplay is not claimed.

Primary source inspection: [portable configuration](https://github.com/melonDS-emu/melonDS/blob/1.1/src/frontend/qt_sdl/Config.cpp), [input](https://github.com/melonDS-emu/melonDS/blob/1.1/src/frontend/qt_sdl/EmuInstanceInput.cpp), [main window](https://github.com/melonDS-emu/melonDS/blob/1.1/src/frontend/qt_sdl/Window.cpp), and the official release's symbol table. Cached source/evidence is in `.tool-cache/research/library-followup/`. No upstream emulator implementation or PGCS code is copied into Broomm.

## PS3 firmware and add-ons

On Play, session supervision holds the coordinator/writer exclusion while checking configured firmware. A valid private installation is reused without network access. Otherwise Broomm reuses its shared managed resource, or requests RomM 5.4's `GET /api/firmware?platform_id=…&missing=false` and its authenticated content endpoint. Exactly one available PUP for that platform is required. Transfer size, RomM MD5 and PUP header are verified before native import. Firmware is atomically published to managed resources and then copied into the active profile's private RPCS3 portable tree. Old incomplete staging is recovered only with a matching ownership marker and no native writer alive. Failures retain existing resources and progress. Tokens need `firmware.read`; old saved grants can require signing in once again. Read-only accounts retain their reduced-scope login fallback.

`Ps3Addons` uses the same user-facing automatic/manual reconciliation workflow as 3DS. Supported inputs are unpacked matching `.pkg` updates/DLC and exact-content-ID `.rap` license files provided in the game's RomM manifest. PKG magic/content ID and the base PARAM.SFO title/region are verified before import. Updates precede DLC. Unknown alternate title-ID relationships are refused rather than guessed. Unhashed sources are revalidated; verified source fingerprints avoid redundant downloads/imports.

RPCS3 imports into private scratch storage, never the player's profile. Dart validates resulting SFO identity/version and a SHA-256 file inventory before publishing an immutable shared generation. Per-profile deployment journals ownership of `dev_hdd0/game/<TITLE_ID>` and specific RAP files only; savedata, firmware, account identity and unrelated content stay outside that boundary. Other profiles receive the verified generation before play. Removal reconciles all private profiles, retains content shared by another installed ROM version, and retires tracked generations with an external durable deletion checkpoint. Unknown/modified native files stop cleanup with an actionable error.

The pinned RPCS3 CLI requires `--headless --installfw=…` or `--installpkg=…`; `--no-gui` explicitly refuses installation. Its measured d08d568d build completes headless firmware installation, writes a native success checkpoint, then aborts in the uninitialized emulation object's teardown. Broomm accepts only that exact status -6 + teardown diagnostic + native success checkpoint, followed by independent content validation. Other failures remain failures. Bounded installer logs are retained in `diagnostics/rpcs3-install-<UTC>.log` (1 MiB each, newest ten). Source: [pinned CLI/import implementation](https://github.com/RPCS3/rpcs3/blob/d08d568d/rpcs3/rpcs3qt/main_window.cpp) and [headless lifecycle](https://github.com/RPCS3/rpcs3/blob/d08d568d/rpcs3/headless_application.cpp).

`native/installer_guard.c` is a small Broomm C interop component holding the same stable writer lock inside the native installer until process exit. The parent still owns the coordinator. Thus an orphaned installer cannot race another game's restore or scratch recovery. It is bundled precompiled; Dart owns all installation policy, download, validation, publication and cleanup. The child sandbox permits writes only to private scratch and the exact writer-lock file, with no network. Tests prove live-child exclusion, orphan exclusion, and rejection of held/linked locks. No user needs a compiler.

An isolated real RPCS3 import of the supplied PUP succeeded and was reused for two profiles with one fixture-server transfer. The PS3 add-on workflow tests use controlled package/native-import fixtures; no supplied real PS3 update/DLC PKG was available for a native installation test. Owner-authenticated RomM firmware/PKG transfers and gameplay with that content remain acceptance work.

## Switch and complete playable-system save boundaries

All currently playable integrations now have ordinary progress adapters: SNES, GameCube, Wii, 3DS, PS3, Nintendo DS and Switch. This does not make every file format, emulator build or native host validated. RPCS3 and Ryubing expose no supported state format in this slice.

Ryubing's first launch performs a supervised cold initialization, observes the actual native program ID from its bounded startup output and closes the emulator normally before cloud restore. The original SHA-256 ROM binding described in this milestone was replaced by an installed-publication/metadata binding in the [launch recovery follow-up](session-recovery.md); launch and idle save discovery no longer hash ROM contents. The subsequent gameplay launch uses that prepared storage. This is shown as loading, before pairing. An uninitialized explicit Switch save import may ask for one launch first.

The adapter reads the existing last-opened account from Profiles.json and the committed native IMKV/IMEN save index. It matches program/account/type/rank/index and validates both native ExtraData records before admitting a directory. Only the committed `0/` contents of this exact account save and any matching device save are progress. Working `1/`, global index, Profiles.json, ExtraData, console identities, firmware, keys and other saves are excluded. Capture and restore revalidate the binding, so an account/index change is an error rather than a different user's save. Broomm never writes the native index or creates guessed save IDs. Format is `ryubing-directory-v1`. Save attribute structures were checked against [Atmosphere's definitions](https://github.com/Atmosphere-NX/Atmosphere/blob/master/libraries/libstratosphere/include/stratosphere/fs/fs_save_data_types.hpp) and measured in the pinned real executable, not inferred from an unverified source mirror.

The native Switch check clones existing test storage under a held source lease, binds the actual supplied game's program ID, restores a sentinel to committed storage, resumes the real game until its native working tree consumes it, closes normally, and verifies capture excludes system metadata. This proves the native file boundary/consumption for that build and game, not real in-game progress on two devices. The owner's original profile/progress is untouched.

Failed diagnostic runs remain in the evidence directory. Tests were not skipped or relaxed to conceal these failures.

Follow the [README walkthrough](../README.md#verify-downloads-ds-and-ps3-resources). Run Flutter tests/build/native tools serially. Native fixtures use isolated copies and synthetic devices; close interactive Broomm games first. Render tools create offscreen PNGs without desktop automation. Evidence stays under `.tool-cache/research/library-followup/`; remove isolated fixture directories only after all native children exit. Do not delete normal `broomm-data` to clean test artifacts.

Native acceptance is macOS arm64 for the pinned pack. Linux/Steam/gamescope, Windows, Android external-emulator access, physical controller play, real gameplay saves/states across devices and arbitrary newer emulator builds remain unverified. The six existing native emulator smoke checks guard shared bridge behavior; they do not turn these limits into cross-platform acceptance. RomM 5.4 still lacks an atomic expected-hash upload guard; the previously documented simultaneous-writer race remains.
