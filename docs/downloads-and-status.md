## Implemented behavior

Downloads have a saved limit of 1–6 active game jobs, default 3, with independent progress, cancellation and failures. Per-game OS locks and private stages allow transfers to overlap; shared receipt publication and account queue checkpoints stay serialized. Recovery removes only abandoned stages for the game whose lock is held. Lowering the limit lets current transfers finish. Emulator add-on work remains serialized under its writer lease. Canceling an admitted operation waits for rollback; canceling a waiter cannot admit a later writer ahead of live work. Completed reservations are released.

Normal game downloads no longer reread payloads for CRC32. **Verify game checksums** requests that optional scan. Complete HTTP/manifest sizes, file lengths, staged publication and receipt readback still apply; receipts distinguish `transfer-size` and `crc32`. Independent save, firmware, package and executable checks are unchanged. A warm 64 MiB local production-path fixture measured CRC phases of **226,896 µs** and **211,259 µs**, versus **128 µs** for size-only validation. Total copy/install times were 419/334 ms versus 141 ms. These are phase timings, not internet throughput or cold-disk benchmarks.

Home tiles display active-profile cloud status without preparing emulators or reading native save payloads. Green cloud/check means a confirmed sync; amber cloud/sync means pending, active or awaiting first verification; red cloud/off means conflict, damaged/interrupted recovery or unsupported progress. Confirmed empty progress has an acknowledgment distinct from unknown first state. Tooltips explain each state. Refreshes follow library load, cloud actions, retries and session completion, with context/revision guards. A badge reflects the last known result rather than continuous remote freshness; its optional read cannot delay repeat launch.

Default emulator cards have a green outline. **Open emulator** launches without a ROM using the same profile-private HOME/XDG/portable data, scoped write sandbox and native writer guard. It does not run gameplay controller preparation. Games, setup/removal and profile changes cannot race it. Quit through the emulator's own UI; actual process exit restores Broomm and releases the lease. RetroArch/Dolphin game preparation now patches required routing while retaining unrelated preferences, including graphics choices. No new library or automatic emulator update was introduced.

The dock now uses **held L2 Shift / R2 Enter** in Flutter game keys and the macOS, Windows, Linux and Android adapters. Start remains an alternate submit action. Native macOS GameController snapshots verify callbacks and overlapping held-trigger release. Physical controllers and other-host native execution remain separate checks.

## RPCS3 loading and Gran Turismo 6

Both pinned d08d568d RPCS3 builds expose six plain atomic file/module/estimate counters. The existing bridge reads them through hash-pinned symbols and the executable slide, without dereferencing C++ progress strings or changing dialogs, shader settings or cache paths. Bounded repeated snapshots reject inconsistent tuples. Protocol 4 adds optional `loading` data; invalid/absent counters cannot break controller status. Flutter shows the native phase estimate and file/module counts, becoming indeterminate between phases. The bar can reset; it is neither a whole-launch percentage nor an ETA. Pairing still requires independent input/pause acknowledgment.

Primary sources: pinned [counter declarations](https://github.com/RPCS3/rpcs3/blob/d08d568d/rpcs3/Emu/system_progress.hpp) and [native dialog calculation](https://github.com/RPCS3/rpcs3/blob/d08d568d/rpcs3/Emu/system_progress.cpp). ARM/Intel addresses are in their separate setup symbol assets, tied to the existing executable hashes. No emulator implementation source was copied.

The actual encrypted 3D Dot Game Heroes ISO/key was read-only, using fresh isolated profiles. Checks observed **271 distinct tuples on ARM** and **293 on Intel/Rosetta**, reached input/pause readiness and confirmed normal supervised exit. The two cold launches/checks took **11m39s** together. This establishes loading/readiness, not gameplay or physical input acceptance.

The supplied 25,293,815,808-byte Gran Turismo 6 ISO contains multi-extent `GT.VOL` records alongside an ordinary EBOOT. The reader previously rejected those unrelated entries while finding title metadata. It now bounds directory names first and applies supported-record/extent checks to the selected path. Ambiguous, truncated, out-of-bounds and multipart metadata still fail. It neither extracts nor interprets GT.VOL; see [ECMA-119](https://ecma-international.org/publications-and-standards/standards/ecma-119/) for the multi-extent distinction. The production reader identified **BCUS98296** in **25 ms**, retained its adjacent key and observed unchanged image size/mtime. This repairs the reported title-inspection error. Installation and in-game visibility of that particular DLC remain owner verification; ordinary package identity/license checks remain.

## Verification and limits

- **247 Flutter tests pass**, with clean analysis. Regressions cover overlapping held transfers, limit changes, independent failures/cancellation, per-game/cross-process locks, surviving foreign stages, size-only truncation rejection, cloud states, preferences, loading-widget transitions and admitted-writer rollback.
- Two native macOS GameController tests pass. All seven no-game choices start privately and exclude competing sessions. Those fixtures use signals solely to clean up disposable children; normal user preference changes/quit remain owner acceptance. Three guard checks verify live/orphan exclusion and linked/held-lock rejection.
- Inspected desktop/compact offscreen renders cover default/Open cards, dock shortcuts, downloads and all cloud badges. These are widget renders, not desktop computer control or physical observations.
- Native loading, read-only GT6 inspection and the checksum benchmark are separate checks. They wrote no owner profile/save, remote asset or graphics setting. No new dependency or OS installation was introduced.

Failed logs are retained. Initial Flutter sockets were denied by the sandbox; the authorized unsandboxed run resolved that environmental failure. The old blanket staging-cleanup test was replaced with the per-game ownership boundary and a foreign-stage sentinel. New card actions changed compact traversal. Best-effort badge reads briefly delayed repeat launch and are now independent. Completed add-on tails retained a widget-clock continuation at teardown and are now cleared. A render assertion initially counted Home's existing connection icon; it now targets each badge label.

The native harness initially needed an import/absolute child path, then tried cancellation during cold compilation. It now waits for real readiness using the established cold-start budget. Generic macOS/Qt no-game quit experiments were inconsistent; their native close code was removed. Production uses normal emulator UI and never force-quits a configuration writer. Qt's [quit contract](https://doc.qt.io/qt-6/qcoreapplication.html#quit) permits refusal; a request is not evidence of exit.

Evidence and disposable data are in `.tool-cache/research/downloads-status/`; component hashes/release verification are in the companion JSON. The release is an Apple Silicon development build using this checkout's pinned pack, with Intel RPCS3 through existing Rosetta. Other-host runtime checks, Steam/gamescope, manual emulator settings, owner cloud behavior and GT6 DLC gameplay remain separate. README provides prerequisites, commands, external effects and cleanup.
