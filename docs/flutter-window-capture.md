# Shared Flutter window-capture API

Current decision: the owner canceled window capture on 2026-10-22. This document is retained as historical research; no capture library is selected or implemented. See [native RPCS3 loading progress](downloads-and-status.md).

Research, 2026-10-22. This revises the native-adapter-only recommendation in [the initial preview investigation](loading-preview-and-keyboard.md). Flutter libraries can abstract desktop window capture. No capture package is installed and no preview or capture permission request is implemented by this change.

## A usable common API exists

[`flutter_webrtc` 1.6.2+hotfix.4](https://pub.dev/packages/flutter_webrtc) exposes `desktopCapturer.getSources(types: [SourceType.Window])`, source IDs/thumbnails, `navigator.mediaDevices.getDisplayMedia(...)` and `RTCVideoRenderer`/`RTCVideoView`. A local media stream can be rendered directly in the existing loading screen without a server, peer connection, encoder upload or another top-level window. `audio: false` avoids requesting audio capture. Limit the requested video rate and size to the preview budget. Its source thumbnails also offer a rudimentary low-rate preview, at the cost of JPEG allocation/decoding and polling.

The package is MIT licensed; its bundled WebRTC runtime has its own third-party notices and licensing to retain. The Dart dependencies include `dart_webrtc`, `webrtc_interface`, `path_provider`, `collection`, `logger` and `web`, with further transitive/platform packages. This is a substantial media runtime for a small preview, rather than a lightweight screenshot binding. macOS declares WebRTC-SDK `150.7871.01` and weak-links ScreenCaptureKit. The Linux/Windows build downloads native libwebrtc artifacts with x64/arm64 selection; those build recipes are not proof that each shipped binary captures correctly on either architecture. Any adoption must pin the package/lockfile, native artifacts and hashes in project-managed caches, inventory notices, and package the runtime so players need no compiler or global installation. The reviewed upstream CMake downloader does not supply an expected archive hash; distribution verification must address that before release.

The maintained repository contains recent capture lifecycle/worker-thread changes, while upstream reports also describe failed window captures returning a dead track. Reviewed C++ startup can fail `SelectSource`/focus, and not all native failure callbacks become actionable Dart errors. Treat successful `getDisplayMedia` completion as only stream creation: require a first rendered frame within a bound, detect stalls/window replacement, and stop tracks/dispose the renderer on readiness, cancellation, exit and route disposal. Late asynchronous results must dispose themselves if the session generation changed. Capture failure must leave the loading/pairing flow usable.

Primary API/source: [desktop capturer implementation](https://github.com/flutter-webrtc/flutter-webrtc/blob/db81cea2730ae65b53fd3ffa97f45ad71200344a/lib/src/native/desktop_capturer_impl.dart), [local capture sample](https://github.com/flutter-webrtc/flutter-webrtc/blob/db81cea2730ae65b53fd3ffa97f45ad71200344a/example/lib/src/screen_capture_api_sample.dart), [native capture lifecycle](https://github.com/flutter-webrtc/flutter-webrtc/blob/db81cea2730ae65b53fd3ffa97f45ad71200344a/common/cpp/src/flutter_screen_capture.cc), [native downloads](https://github.com/flutter-webrtc/flutter-webrtc/blob/db81cea2730ae65b53fd3ffa97f45ad71200344a/third_party/CMakeLists.txt), [macOS dependency](https://github.com/flutter-webrtc/flutter-webrtc/blob/db81cea2730ae65b53fd3ffa97f45ad71200344a/macos/flutter_webrtc.podspec), and [reported Windows failure](https://github.com/flutter-webrtc/flutter-webrtc/issues/2137). The source revision is a reviewed snapshot, not a claim that every main-branch fix is present in the published release.

## What the abstraction cannot guarantee

The plugin also registers Android/iOS implementations. Adding it can increase Android's shipped runtime even while Broomm's agreed Android flow does not use previews; measure packaging per target before adopting it. A desktop-only feature flag in Dart alone does not remove native plugin libraries from an Android build.

On macOS, capture still requires Screen Recording consent, and obscured/minimized/compiler-dialog behavior needs a native check. On Windows, the reviewed libwebrtc source has conditional Windows Graphics Capture support and fallback behavior that depend on the native binary's build flags. On Linux the reviewed wrapper enables PipeWire for **screen** sources, while constructing window sources through a separate window capturer. Therefore `SourceType.Window` support on X11 does not establish unattended window capture on native Wayland or gamescope. Portal screen-sharing may let the person choose an application window, but that is compositor/portal behavior, not automatic process selection guaranteed by the Flutter API. Preserve Android's agreed external-emulator scope.

The Dart source model exposes an ID and title, not a verified process identity. Picking the first title containing “RPCS3” is insufficient. Correlate the captured native window with the supervised child and launch generation, or require an explicit portal selection where the platform prevents that correlation. Never silently replace a missing window with a whole-display source. Follow owned compiler/progress dialogs and the eventual game window; do not capture other applications. See [libwebrtc's source-list backend](https://github.com/webrtc-sdk/libwebrtc/blob/9f6a87af46a5810a452aa20306c705b7c5269fbe/src/rtc_desktop_media_list_impl.cc) and [capture backend/selection](https://github.com/webrtc-sdk/libwebrtc/blob/9f6a87af46a5810a452aa20306c705b7c5269fbe/src/rtc_desktop_capturer_impl.cc).

## Alternatives and proposed choice

| Choice | Benefit | Cost / fit for Broomm |
| --- | --- | --- |
| Flutter WebRTC | Common macOS/Windows/Linux API and a local live video widget; most useful shared-library candidate | Large bundled native dependency and notices; source ownership and Wayland/gamescope still need adapters/acceptance; careful first-frame/cancellation handling |
| [`screen_capturer` 0.2.3](https://pub.dev/packages/screen_capturer) | MIT, smaller screenshot-focused plugin; advertises all three desktop hosts | Interactive screenshot selection, not a continuous stream API; Linux window capture is limited to the current window; Windows requires ATL build tooling. Repeating screenshots does not solve unattended emulator selection. |
| [`flutter_screen_capture` 2.0.1](https://pub.dev/packages/flutter_screen_capture) | Small display/region capture and a rudimentary live area widget | Its own documentation says Linux, multiple displays and Retina capture are unsupported; screen coordinates can capture Broomm instead of an obscured emulator. |
| [`screen_capture_kit` 2.0.0](https://pub.dev/packages/screen_capture_kit) | BSD-3-Clause native Dart ScreenCaptureKit bindings, direct windows/live streams and build hooks | macOS-only; recently published, still needs target/lifecycle/texture integration and a separate Linux/Windows implementation. Not a shared desktop solution. |
| Broomm's own small capture adapters | Direct control over owned windows, textures, queues and lifecycle; no WebRTC runtime | More implementation and native verification per host; Linux portal/PipeWire distribution remains a dependency decision. |

Recommendation: if the owner accepts the additional runtime, prototype **Flutter WebRTC**, using a video-only local stream at 640×360 and 5–10 fps inside Broomm's loading screen. Measure actual package size, frame delay, CPU/GPU cost and cancellation. Start with the available Mac, then make the same-game gamescope/Wayland check an independent acceptance gate. A 1–2 fps thumbnail can be a fallback experiment where streaming fails, but is not evidence that Linux window selection works. If runtime size outweighs shared-code savings, retain the proposed small native texture adapters. This research is the concrete dependency proposal; the owner has not yet chosen a new package.
