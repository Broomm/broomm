# LAN controller and second screen feasibility

The [24 November implementation](../remote-screen.md) follows this investigation.

13 November 2026 · Proposal based on Broomm revision `417f3cb` and upstream source inspection.

Broomm can use the same LAN connection model on Android, macOS, Linux and Windows. The desktop host would run the game, show the main screen and keep ownership of the active profile, emulator and saves. The second Broomm instance would forward its controller and, when the host emulator supports it, show the secondary screen. Launcher navigation is the simplest part. Gameplay input needs a verified route into the host emulator. Video needs a capture backend for the host and a way to identify the emulator's secondary output. [Product requirements](../../PROJECT.md#starting-and-controlling-a-game) · [Session ownership](../architecture.md#session-and-synchronization-lifecycle)

## Controller forwarding

Android's `MainActivity` already reads gamepad buttons and joystick axes in the foreground. It currently turns them into launcher actions, so Broomm needs a separate source of per-device button presses and releases, both sticks, triggers and D-pad state. Normalize controller variants at that boundary and clear state on device removal or loss of focus. Desktop clients also need a full-state reader where their current launcher adapters expose only navigation actions. Dart can share controller state, pairing, transport and connection UI across the four platforms. Android can send input while Broomm is open using ordinary controller APIs. Its local games still use the external emulator handoff. [Android input](../../android/app/src/main/kotlin/app/broomm/broomm/MainActivity.kt#L111) · [Launcher input](../../lib/src/shell/controller_input.dart) · [Android controller guide](https://developer.android.com/games/sdk/game-controller/controller-input)

On the host, route remote input through the same launcher actions as a local controller. For gameplay, register the remote controller as a source in the emulator bridge and let the existing pairing screen assign it to a player. The macOS and Linux bridges already publish emulator-runtime device identities, gate gameplay input and drive SDL virtual ports. They need a production remote source and a private local channel for the host to deliver samples. Keep the LAN connection in the Flutter app and the bridge scoped to the supervised process. Keep frame-rate samples out of the bridge's command-file path, which handles changes such as applying assignments and pausing. An SDL virtual device created in the launcher lives in a different process from the emulator. [Launcher dispatch](../../lib/src/shell/app.dart#L1088) · [Session commands](../../lib/src/session.dart#L861) · [macOS input bridge](../../native/session.inc#L519) · [Linux input bridge](../../native/linux_input.inc) · [Linux RetroArch bridge](../../native/linux_retroarch.c)

Start with one remote controller alongside local controllers. Give its connection and device separate identities, and bind each assignment to the current host session. Preserve brief button presses and releases while coalescing superseded analog samples. Expire the input at the bridge if fresh samples stop, including when the host app stalls or exits. Remove the source and let the current pause and pairing flow handle an assigned controller's disconnect. A reconnect starts neutral and cannot replay old input or resume a paused game by itself. Verify that the active game consumes the assigned port and that menu chords reach only the intended input path. [Pairing model](../../lib/src/pairing.dart) · [Disconnect and pause flow](../../lib/src/app_model.dart#L203)

### Controller input inside the emulator

Follow-up on 24 November 2026, checked against Broomm revision `a5a1ebb` and Guestpad's current source. The proposed receiver can operate entirely inside Broomm and its supervised emulator. Launcher navigation calls Broomm's actions directly. Gameplay input enters the emulator through its existing Broomm bridge. SDL's virtual joystick implementation keeps its devices and their input state in the process's SDL runtime. Broomm already uses those internal controller ports, and its macOS native experiments exercised synthetic button and axis input inside real emulator processes. This provides a driverless foundation for the LAN receiver. [SDL virtual joystick implementation](https://raw.githubusercontent.com/libsdl-org/SDL/release-3.4.0/src/joystick/virtual/SDL_virtualjoystick.c) · [Executed macOS validation](injection-validation.md#what-was-actually-tested)

Guestpad uses PadLink's installed macOS driver to publish a DualShock 4 through the operating system's HID device layer. Broomm's process-local controller ports have no PadLink dependency or driver-extension activation step. Each supported emulator must still load the verified bridge and consume its assigned input route. Astris already has a separate bridge that writes directly into its internal controller backend. The next remote-input milestone must prove network samples through these routes, including stale-input neutralization and reconnect behavior. Coverage remains specific to the emulator builds and hosts with working bridges. [Guestpad setup](../../../guestpad/README.md#setup) · [PadLink adapter](../../../guestpad/Sources/GuestpadCore/PadLink.swift) · [Astris bridge](../../native/astris_bridge.m)

Capture the secondary output from the same emulator process. The adapter needs to resolve the main and secondary roles in addition to the owning process and its start identity. Both windows can belong to the same process. The host's current focus helpers primarily identify one game window, so validate the correct window stays foregrounded when a pairing menu closes or fullscreen changes. Test capture when the secondary window is covered, minimized and moved across Spaces or workspaces. If the platform requires it to stay visible, verify the resulting desktop layout before calling it usable. When the source disappears, stop that stream and offer an explicit return to a local two-screen layout where the adapter supports it. ## Platform limits

| Platform | Client and host implications |
| --- | --- |
| **Android** | Start as a controller and second-screen client. Show the LAN connection entry independently of RomM sign-in, then keep it foregrounded during play. Check local-network permission as the target SDK changes. Hosting an Android external emulator would need its own supported input and separate-output contracts. [Android LAN permissions](https://developer.android.com/privacy-and-security/local-network-permission) |
| **macOS** | Start with the existing host session bridge. ScreenCaptureKit can target a single window with Screen Recording permission. It starts at macOS 12.3, so gate it separately from Broomm's macOS 12.0 deployment target. Verify Local Network permission on the packaged app for routes that require it. [Single-window capture](https://developer.apple.com/documentation/screencapturekit/sccontentfilter) · [ScreenCaptureKit availability](https://developer.apple.com/videos/play/wwdc2023/10136/?time=24) · [Local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) |
| **Linux** | Validate desktop X11/XWayland, native Wayland and Steam Gaming Mode independently. On Wayland, window sharing depends on the compositor's ScreenCast portal and its PipeWire source selection. The Armada forks' DRM lease goes directly to a physical panel and does not supply a second ordinary window to capture. An unavailable or unverified window source leaves controller-only play available. [ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html) · [Armada leases](../linux-standalone.md#ayn-thor-dual-screen-feasibility) |
| **Windows** | The launcher has controller navigation, and Windows Graphics Capture can target application windows. The current `GameSession` only launches on macOS and Linux, so Windows can be a client before native host gameplay is delivered. A Windows capture demo alone would leave the launch and controller-routing work outstanding. [Host launch guard](../../lib/src/session.dart#L356) · [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) |

## Transport and dependency choices

Use explicit host activation and local confirmation. A first version can show a host address and verify the connection identity out of band before authorizing control. Keep the session encrypted and scoped to Broomm controls and the approved output. A short human-readable pairing code needs expiry and bounded attempts. Use a vetted secure transport and pin or verify the host identity at pairing. This works on a reachable LAN without RomM credentials, a relay, or port forwarding. Discovery can be added independently. A disconnect must leave emulator supervision, save locking and finalization with the host. [Dart TLS API](https://api.dart.dev/dart-io/SecureServerSocket-class.html)

| Option | Benefit | Cost and verification |
| --- | --- | --- |
| **Dart TLS with a small control protocol** | Fits the controller-only milestone with the shipped Dart runtime and the same connection code on every client. A dedicated connection keeps controls separate from video queues. [Dart TLS API](https://api.dart.dev/dart-io/SecureServerSocket-class.html) | Broomm owns TLS identity provisioning and verification, pairing, bounded messages, deadlines and backpressure. TCP retransmission can delay later input on lossy Wi-Fi. Measure it and expire input when the sender or receiver falls behind. |
| **`flutter_webrtc` for video** | Maintained MIT Flutter wrapper over libwebrtc with video and data channels on all four targets. A low-latency video track provides a shared receiver and transport, with optional partially reliable channels for analog updates. Broomm supplies authenticated LAN signaling. [Platform matrix and license](https://github.com/flutter-webrtc/flutter-webrtc) · [WebRTC data channels](https://www.w3.org/TR/webrtc/#rtcdatachannel) | Adds Dart dependencies and native runtimes. Review bundled notices, Android ABIs, both macOS slices, Windows x64 and Linux x64/ARM64. Pin the artifacts and validate hashes in project-managed caches, since the reviewed native CMake download has no expected hash. Test the packaged plugin's exact window source, first decoded frame, permission denial, stalled capture, cancellation and resource disposal. Its exposed source ID and title need platform or emulator evidence to establish ownership. [Native download recipe](https://raw.githubusercontent.com/flutter-webrtc/flutter-webrtc/main/third_party/CMakeLists.txt) · [Capture source metadata](https://raw.githubusercontent.com/flutter-webrtc/flutter-webrtc/main/common/cpp/src/flutter_screen_capture.cc) · [Earlier capture audit](../flutter-window-capture.md) |
| **Native capture and codec adapters** | Direct control over window identity, frame queues and the native texture. ScreenCaptureKit and VideoToolbox on macOS and MediaCodec on Android give a path to a small two-host experiment. [VideoToolbox low-latency encoding](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_enablelowlatencyratecontrol) · [MediaCodec](https://developer.android.com/reference/android/media/MediaCodec) | Requires maintaining capture, encoding, decoding and video delivery across desktop systems, including Linux compositor and hardware-encoder differences. Codec availability and distribution would need target-specific verification. Broomm would own recovery from frame loss, congestion and cancellation unless it adopted a separate media transport. |

Prototype window capture before considering an emulator renderer export. An export could survive compositor restrictions and remove the local secondary window, but would require per-emulator and renderer work plus review of the build, distribution and license obligations. Start with unmodified emulator packages and Broomm-owned configuration. The prior cancellation of RPCS3 loading-preview capture remains scoped to that workflow. [RPCS3 decision](../../PROJECT.md#starting-and-controlling-a-game) · [Configuration ownership](../emulator-support.md#configuration-ownership)

## Proposed validation order

1. **Controller on Android, host on macOS, then Linux.** Pair over the LAN and drive Home, the keyboard and a real RetroArch session. Verify a short tap, both sticks and triggers, a local and remote assignment, a menu chord, disconnect while holding inputs, reconnect, and normal save finalization. Test loss and stale packets independently of the video path.
2. **melonDS on the same LAN.** Use one pinned desktop emulator and a title with distinct changing content on both screens. Confirm the computer displays the top screen, the client receives only the bottom screen, and host controller focus and pause/resume still work. Test capture denial, window replacement, Wi-Fi interruption and orderly teardown. Measure input-to-emulator delay, host-to-client frame delay, dropped frames and emulation frame time with and without streaming. Add touch for a DS title that requires a tap and drag, and verify release during disconnect.
3. **Expand by verified capability.** Repeat for Azahar, then desktop clients and host backends as their native routes become available. Keep ordinary desktop Linux and Steam Gaming Mode as separate checks. Measure package size and runtime dependencies before selecting a media library for distribution.

This assessment establishes source-level feasibility. Controller latency, capture behavior and end-to-end gameplay still need native measurement on the proposed host and client pairs.
