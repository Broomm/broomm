# PPSSPP and Eden integration

This milestone adds PSP through **PPSSPP 1.20.4** and **Eden 0.2.1** as a second Switch choice, retaining Ryubing as the existing default. The reviewed native runtime is macOS ARM64. Eden's upstream macOS build is explicitly experimental. Linux, Windows, Android, physical controllers and cross-device gameplay require separate native acceptance. Other platforms remain visible/downloadable; no PS4 emulator is added.

## Installation and owner walkthrough

Prerequisites are the pinned local bundles used by the current setup importer: `prototype-data/ppsspp/PPSSPPSDL.app` and `prototype-data/eden/eden.app`. The existing development checkout has reviewed private copies. A new machine needs those exact prepared bundles or an explicitly reviewed new recipe. Broomm's app ZIP contains the Dart application, setup inventories and precompiled bridges, not emulator executables, games, firmware or keys. It does not install an emulator, compiler or dependency system-wide.

1. Open **Emulator Settings → PlayStation Portable → PPSSPP → Setup**, review the expanded card and confirm. Download an ISO, CSO v1 or PBP PSP game from the Store, then choose **Play** on Home. PPSSPP uses HLE and needs no console BIOS file. Pair one pad with **L1 + R1**, test the illustrated PSP controls, and hold Start to play.
2. During play, **R3 + Select** pauses the native core and opens the existing Flutter menu. **Controller pairing** permits reassignment and **L3 + R1** swaps both face-button pairs without restarting. Disconnecting the paired source pauses and reopens pairing. Close PPSSPP normally to flush progress and return to Home.
3. Use the game's cloud-save menu to inspect timestamped **BROOMM** versions or explicitly import/export native progress. PSP ordinary saves are ZIPs of the matching savedata directories, preserving `PARAM.SFO`, data and native companion files. They are not raw `.sav` containers. Native `.ppst` states and their `.jpg` companions remain in exact executable/game-revision/host groups. A different region/serial or unknown homebrew identity is rejected rather than assigned another game's save.
4. For PSP DLC, put the native directory inside a RomM `dlc/` ZIP, such as `PSP/SAVEDATA/ULUS10340DLC/CONTENT.EDAT`; `PSP/GAME/<matching serial>/...` is also accepted. Explicit loose native paths under `updates/` or `dlc/` work too. **Download Updates and DLC** reuses the validated generation and installs into each profile before launch. Static owned files stay outside cloud progress; removing the game deletes them and retains newly created saves. Generic PSP PKG installers, game-specific patch boot chains and differently named serial destinations are not implemented. PPSSPP itself does not implement a universal `sceGameUpdate` installer; this is native-file installation, not a claim that every PSP patch can run.
5. Open **Emulator Settings → Nintendo Switch → Eden → Setup**, then **Set as default**. The two emulators have independent application/configuration/NAND data; the existing Ryubing default is unchanged until selected. Missing Eden resources follow the existing RomM contract: exactly one firmware ZIP, `prod.keys` and `title.keys`. Configured resources are preserved. Firmware or emulator updates never run automatically.
6. Choose a Switch game on Home. Broomm prepares the selected emulator's own content records, initializes its native game/account identity if needed, restores this profile's ordinary cloud save and then opens pairing. Eden provides four logical Pro Controller ports. Pairing, native pause/live remap and disconnect handling use Eden's own SDL/HID/core state. Its ordinary cloud ZIP uses the same logical `save`/`device` areas as Ryubing, without copying either emulator's console accounts, firmware or indexes. Neither Switch backend provides cloud save states.
7. **Download Updates and DLC** checks RomM afresh. Eden validates the native base/title association, extracts encrypted NCAs into private NAND, checks their native content-ID hashes and imports supported common ticket title keys into its private generated key file. It currently accepts **one update NSP per game**, plus multiple matching DLC NSPs. Multiple update packages are reported as ambiguous; Ryubing retains its existing native highest-version selection. Unsupported/personalized tickets require configured title keys. Removal uninstalls owned content from both backends across profiles, retaining saves and unrelated files; generated key configuration is retained.
8. **Open emulator** opens either application's private settings without a game, retaining the writer lock until native exit. Quit normally before playing or removing an emulator. Rendering preferences survive normal Broomm launches. PSP's memory-stick/bookmark preferences are scoped to the child; they do not overwrite a system PPSSPP preference domain.

Managed outputs are under `broomm-data/emulators/`, `broomm-data/profiles/<profile>/emulators/ppsspp/` and `.../eden/`. PSP uses `user/PSP/{SYSTEM,SAVEDATA,PPSSPP_STATE,GAME}`. Eden uses `config/eden/qt-config.ini` and `data/eden/{keys,nand}`. Shared add-on generations are under `broomm-data/addons/<server>/<rom>/psp/` or `switch-eden/`; cloud history/recovery remains in the existing progress store. Confirmed game deletion removes shared payload/artwork and owned add-ons, preserving every profile's progress. Emulator removal preserves private settings/progress. Test directories are disposable `.tool-cache/research/psp/` and `.../eden/`; remove them only after their fixture processes exit. No owner profile or remote RomM save was modified by these checks.

## Native evidence and corrections

- **PPSSPP / N+ and Puzzle Bobble Pocket:** both supplied CSOs boot, pair, read real native PSP button bits, swap face buttons, resume after paused remap, disconnect/reassign within the same PID and close normally. An initial successful run produced native savedata for both games and passed cloud readback/export/restore. N+ is the required repeatable ordinary-save fixture. Puzzle Bobble only writes ordinary progress after gameplay results; its saved-state previews established that repeated button input sometimes stops at round start and sometimes clears a round. Final checks accept that native distinction and verify complete state-only cloud bundles when it has not written savedata. Native state creation, load and restore pass separately. This is automated synthetic-source evidence, not physical-pad or completed-game acceptance.
- Core `BootState::Complete` was initially too early: `EmuScreen::ProcessGameBoot` later rewrites the running state. Puzzle Bobble reproduced a pause flap that disabled joining. The bridge now verifies hash/instruction-pinned frontend completion under a nonblocking screen-manager lock before exposing pairing. No timing delay or fabricated pause acknowledgment replaces that check.
- **Eden / Pokémon Quest:** the native console reports program `01005d100807a000`, exactly two paired console ports, actual Npad button bits before/after face swap, pause/resume and disconnect pause. The final fixture installs the supplied matching update before control checks, as the ordinary download flow does. A seeded marker exercises its ordinary native-directory export/readback/restore; this does not establish a game-created save point. Changing the native account invalidates an old progress boundary. Both legacy and migrated native save paths reject links and preserve missing-versus-invalid observations.
- The supplied Pokémon Quest update and five DLC packages produce **14 verified NCAs**, survive repeat checks without retransfers, apply to a second private profile, and uninstall from both while retaining fixture saves. Native Eden loading logs confirm the update ExeFS was applied successfully. Recognition/purchase entitlement of every DLC during actual gameplay still requires owner acceptance.
- Eden's self-exec Vulkan probe inherited the writer guard and initially rejected its own parent-held lease. Only the exact opted-in Vulkan-check child skips game/writer interop; the actual emulator retains the native writer lock. Static SDL LTO stubs and device-added callback ordering also required Eden-specific enumeration/deferral. The corrected native test waits for activation's physical-button release gate before submitting input.
- The experimental Eden build produced native graphics/guest faults with other startup fixtures. A repeat of unpatched Quest hit guest `Break 0xE401`; its stack then spun in native kernel shutdown while the Qt close handler waited. The real writer lease and data were retained when normal close timed out. That disposable orphan was identified by exact private executable path and sampled. It ignored SIGTERM, so fixture-only SIGKILL was required and its exit was verified; owner gameplay was not signaled. The updated Quest control/save fixture closes normally. This is a measured compatibility limit, not proof that Broomm repairs upstream faults. Native pause uses `EmuThread::SetRunning` and verifies actual paused/powered state; optional UI sleep/Discord/play-time callbacks are not treated as pause acknowledgments.

The [machine-readable record](psp-and-eden-support.json) retains exact source/output hashes, logs, fixture results, failures and release verification. The [colored support matrix](platform-support-matrix.md) distinguishes these checks from pending acceptance.

## Reproduction

Use the pinned project Devbox environment and pre-provisioned Xcode SDK. Prepare source bundles privately and preserve their notices. Explicit capture commands below accept only the reviewed prepared executable hashes; they do not trust arbitrary replacements.

```sh
devbox run -- dart tool/capture_ppsspp_setup.dart
devbox run -- dart tool/capture_eden_setup.dart
devbox run -- bash tool/build_bridges.sh
devbox run -- flutter analyze
devbox run -- flutter test
devbox run -- flutter test tool/check_ppsspp_defaults_test.dart --reporter expanded
devbox run -- env BROOMM_DEFAULTS_SANITIZERS=1 flutter test tool/check_ppsspp_defaults_test.dart --reporter expanded
devbox run -- flutter test tool/check_ppsspp_test.dart --reporter expanded
devbox run -- flutter test tool/check_eden_test.dart --reporter expanded
devbox run -- flutter test tool/check_eden_packages_test.dart --reporter expanded
devbox run -- flutter test tool/smoke_managed_test.dart --reporter expanded
devbox run -- flutter test tool/check_playstation_test.dart --reporter expanded
devbox run -- flutter test tool/check_emulator_configuration_test.dart --reporter expanded
devbox run -- flutter test tool/check_installer_guard_test.dart --reporter expanded
devbox run -- bash tool/build_app.sh --release
```

Run emulator suites sequentially to avoid native device/window contention. Integration media downloads are read-only copies of the supplied catalogue, and cloud writes go to the in-process fixture server. Fixture termination in no-game checks is limited to processes that the test created; production gameplay retains normal native shutdown.

## Provenance and implementation choice

PPSSPP's official [1.20.4 release](https://github.com/hrydgard/ppsspp/releases/tag/v1.20.4) supplies its SDL app, existing SDL2 2.26.5 framework and GPL-2.0-or-later source. The [native DLC guide](https://www.ppsspp.org/docs/getting-started/how-to-install-dlc/) explains why SAVEDATA/GAME folder semantics differ from a universal package installer. Eden's [0.2.1 release](https://git.eden-emu.dev/eden-emu/eden/releases/tag/v0.2.1) supplies an experimental ARM64 macOS app with static SDL2/Qt 6.7.3, GPL-3.0-or-later project source and inherited component notices. The release explicitly retains SDL2. Official download/source archive and original/prepared executable fingerprints are recorded separately; private ad-hoc signing is the only bundle preparation change.

Native bridges are original C interface calls, executable/symbol/instruction guards and OS interop. No emulator implementation or PGCS code is copied. Dart owns package parsing, ownership, configuration, progress and publication. The SDL slot declarations use the already reviewed zlib-licensed SDL headers. The app archive ships no emulator or console assets.

Eden's encrypted NCA header inspection needs a bounded AES primitive. The chosen macOS adapter calls the already supplied Apple CommonCrypto API through Dart FFI; Dart implements sector/container policy. Compared with adding a Dart cryptography package, this adds no package license, transitive dependencies or shipped crypto runtime, but requires a concrete native primitive adapter for other hosts. A separate native installer/helper would duplicate domain workflows outside Dart and add deployment/process failure modes. The primitive is checked against a NIST AES vector and XTS sector round trips, then real encrypted owner NSP metadata/content hashes. No new runtime library, package, service or OS installation is introduced.
