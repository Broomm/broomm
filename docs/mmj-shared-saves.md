# Citra MMJ shared-folder saves

2026-10-30. The owner selected MMJ's shared `citra-emu` folder as the supported Android storage mode. Ordinary save synchronization is implemented through a user-granted Storage Access Framework tree. Private `Android/data` storage and MMJ's Storage Access build remain unsupported. Android device execution is still required; host-side tests and Kotlin compilation do not establish native emulator acceptance.

## Setup and use

1. Install a shared-storage MMJ build and initialize it. Confirm that its active user directory is **Internal storage/citra-emu**, not **Android/data/org.citra.emu/files/citra-emu**. Broomm cannot read MMJ's current storage-mode setting; the setup warning asks the user to confirm this prerequisite.
2. Close MMJ completely. In Broomm choose **Emulator Settings → Nintendo 3DS → Citra MMJ → Configure saves**. Read the warning, choose **MMJ closed · Select shared folder**, and select the shared **citra-emu** directory in Android's folder picker. Grant read/write access. The same shared folder can be connected for several Broomm profiles; each profile's private files and RomM account remain separate.
3. Use **Home → game → Options → Use existing save file** to import an account-owned RomM save when desired. MMJ uses the existing Citra-family title-data ZIP contract, including `00000001.metadata`, the `00000001/` directory and identified extdata. Broomm does not adopt unrelated standalone MMJ progress automatically. The **Backup savefile** and cloud-conflict actions operate on this profile's private copy, not directly on MMJ's live folder.
4. Choose **Play → Emulator closed · Sync and play**. Broomm checks this account's latest BROOMM version automatically, preserves MMJ's previous title saves, copies the selected profile's files into the game's expected native paths, verifies them, then launches the ROM. No desktop controller pairing or overlay is used.
5. Save and exit MMJ fully, then choose **Finish and sync progress**. Broomm captures the session into private storage, appends a timestamped `.zip` BROOMM version or retains a pending offline upload, and restores MMJ's previous standalone saves. Subsequent profiles repeat this swap. Merely returning to Broomm is not evidence that MMJ has stopped.

Folder selection rejects private paths, another app's provider, a parent storage root and subdirectories other than the exact shared `citra-emu` root. Revoked grants or unsuccessful scans fail visibly without treating the save as absent. No all-files permission, root, global SDK change, or new Flutter dependency is needed. A shared folder selected while MMJ actually uses private storage cannot be diagnosed automatically; it is not evidence of the emulator consuming the copied save.

MMJ save-state synchronization and automatic CIA installation remain missing. Existing standalone states for the selected title are temporarily moved aside with the save backup so they cannot be loaded into another profile. States created during a Broomm session stay in its retained private capture; they are not automatically reloaded or uploaded as compatible states. Other titles' states and emulator settings are untouched.

## Ownership and recovery

Dart owns the workflow, journal and cloud decisions. The existing Android MethodChannel performs standard-provider queries and bounded file I/O, including persistent grants, staging, integrity readback and publication. Data streams and queries have cancellation deadlines and limits of 256 MiB per file, 512 MiB per inventory and 4,096 files. The bridge uses a separate stage file and old/new hash checks before replacement; an interrupted delete/rename gap can resume from its known stage. Only save data is hashed here; this does not add a ROM or emulator checksum scan on launch.

SessionLease covers cloud preparation, the shared-folder swap, the external game and finalization. Native document operations also retain the stable OS lock `android/mmj-document-io.lock`; a replacement Flutter activity cannot recover while an earlier native transfer is still running. Activity destruction cancels active I/O and rejects queued operations without treating cancellation as successful publication. Never delete this lock file. A durable `android/session.json` precedes external effects. `android/mmj-swap.json` identifies the account, ROM, native title, selected tree and transaction. Complete private original/working inventories precede the first external write. A session interrupted during preparation completes the known copy and restores its original inventory without uploading the partial preparation as gameplay. A session interrupted after handoff captures progress with the existing unclean-review policy. Private capture publication reuses the cloud store's interruption-safe restore.

After interruption, use **Emulator Settings → Finish previous game session**, or Play's recovery screen, with the original server/profile. The swap receipt independently exposes recovery even if the general session receipt is missing. Close MMJ before confirming. An unexpected outside write is preserved and blocks blind replacement. If normal recovery fails, the session screen offers **Keep MMJ folder unchanged · Finish**. Its confirmation leaves the external files untouched, retains private recovery copies, marks the existing cloud record for review and releases the session without further upload. It also works after restart and with a revoked folder grant. It does not certify uncertain native data as synchronized.

Recovery archives remain under Broomm's Android app-private `android/mmj-session/<transaction>/`; ordinary profile working files live under `profiles/<profile>/emulators/citra-mmj/user`. Completed and explicitly retained transactions have durable completion/resolution records. Do not delete an active journal, clear application data or remove these copies to resolve an unfinished writer. No automatic recovery-archive cleanup is added in this milestone. After all sessions are finished, confirmed independent backups are required before intentionally removing retained copies. Clearing Android app data/uninstalling Broomm removes these private files.

## Verification

All 440 main Flutter tests and two separately scheduled full-size save tests pass, with clean static analysis. Five MMJ regressions exercise the real Dart supervisor, cloud save store and persistent grants through a controlled Android document boundary. They cover first-save BROOMM upload, two-profile swaps and restart, preservation of standalone saves/extdata/states and settings, cancelled/private/revoked grants, held session/transfer locks, deterministic publication interruptions in both directions, outside writes and explicit keep-folder resolution. All Android Kotlin sources compile against the pinned API/Flutter artifacts in the project's Devbox environment. A separate native JVM fixture on macOS verifies the production lock with concurrent activity-style callers and a second process, including that status queries retain OS exclusion, release admits another process and linked lock files preserve unrelated data. CI schedules this independently of the macOS host application tests. These checks do not execute Android's DocumentsUI, real URI grants, filesystem provider or an MMJ APK.

```sh
devbox run -- flutter analyze --no-pub
devbox run -- flutter test --no-pub test/mmj_shared_saves_test.dart test/android_emulators_test.dart
devbox --config tool/android run check
devbox --config tool/android run check-shared-lock
```

Outputs: disposable test directories are removed by teardown; retained verification logs are under `.tool-cache/research/mmj-shared-saves/`; Kotlin emits `.tool-cache/research/android/bridge.jar`, not an APK. No production profiles, emulator directories or real RomM saves were modified by these tests. Native acceptance must verify folder grants across restart, real save load/create, two profiles, offline reconciliation, MMJ closure and recovery on an Android device before describing the route as gameplay-verified.

The [verification record](mmj-shared-saves.json) identifies sources, logs and archive checks. It does not provide an Android APK or establish Android execution.
