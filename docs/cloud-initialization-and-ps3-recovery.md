# Automatic first sync, queue ownership and PS3 file recovery

Implemented 2026-10-23. This follows [downloads and status](downloads-and-status.md); the BROOMM slot/native extension contract remains in [save history](slotted-saves-and-ps3-iso.md). No new dependency, native component or emulator update was introduced.

## Observed causes and changes

The cloud worker previously considered only existing pending/active records. A new installation had neither, so its badge could remain amber until gameplay or an explicit cloud action. Idle work now includes installed games without an acknowledged result and starts after profile activation, library loading, download completion and emulator setup. The periodic worker remains the connectivity fallback. Up to twelve eligible games are handled sequentially per pass, with a single reserved worker, account checks, cancellation/draining and the production SessionLease. Downloads, setup and gameplay take precedence.

Initial sync uses the verified emulator adapter's actual save boundary. A configured build can prepare private progress even before PS3 firmware is installed; this does not start an emulator. When local and managed remote progress are both empty, this is acknowledged without uploading a dummy save. Existing BROOMM progress is restored to an empty device. Divergent existing progress requires a choice and preserves both copies. Other slots/backups are still used only through explicit selection, apart from the existing read-only legacy-managed migration. A missing emulator, ambiguous ROM entry or uninitialized Switch native identity can defer a first sync. Unsupported/damaged observations never become a successful badge. The tooltip is now “Cloud saves waiting to sync.”

The reported `queue.lock` was held by a live older `build/releases/broomm 9.app`, not an abandoned lock file. The app now reads the atomic queue checkpoint when ownership is busy and displays it read-only, preserving actual active/queued/failed states. Refresh acquires the same stable OS lock after its owner quits and enables explicit Retry/Remove. Non-owners cannot release another store's in-process guard; canonical storage identity prevents path aliases from bypassing that guard. The lock inode is never deleted and the other app/game is never killed. New downloads remain blocked while another process owns that account's queue.

GT6's untracked title folder contained **579 files, 477,784,862 bytes**, including game-created installation/database data. The cached DLC package contained eleven files and overlapped existing `PARAM.SFO` and `ICON0.PNG`. Whole-title-directory ownership was the wrong boundary. RPCS3 now owns individual package/license files in a version-2 profile registry. Unrelated files are neither scanned for ordinary deployment nor claimed/deleted. Existing overlapping files are copied, flushed and hash-verified in private `.ps3-addon-originals/<sha256>` storage before replacement. Removing the last Broomm owner restores originals and removes only its package files. Newer Broomm-owned shared files retain their version/owners rather than being downgraded by an older installation.

The file transaction stages verified replacements, publishes a journal, moves old files aside, publishes/readbacks new files and commits ownership before cleanup. Retry rolls a recognized interrupted transaction forward. Changed owned files, wrong title metadata, altered recovery files, links and unknown transaction entries stop safely. Version-1 registries migrate by their recorded files, after any legacy journal is recovered; unrecorded game-created files do not acquire ownership. Existing savedata/configuration is outside these targets. Retained originals remain recovery material even after package removal. Do not run older Broomm copies against a profile after it has migrated.

## Verification and owner walkthrough

All **257 Flutter tests** pass. Final commands/results and source/release fingerprints are in the companion JSON. Regressions cover empty initial sync, managed-slot pull, offline/conflict preservation, cancellation/session locking, independent-process queue contention, non-owner close, read-only refresh/recovery, metadata restoration, legacy migration, interrupted publication and unknown/changed file protection.

The macOS copied-data integration uses the real GT6 title tree and cached output produced by the native RPCS3 installer. Production apply adds nine previously absent files (588 total), preserves every original non-metadata file, reuses the package on a second apply and restores the exact original 579-file inventory on removal, including original metadata. Final measured apply/reuse/removal times were 254/73/367 ms on this host. A separate check reads the real GT6 queue checkpoint; its initially observed older app had exited by the final check, so ownership was available. Deterministic independent-process lock tests establish read-only observation under a held lock. Source profile inventory and registry are checked unchanged under the production session lock. No server assets, settings or emulator caches were modified. This establishes file deployment/recovery; it does not establish in-game DLC visibility or new native PKG import/gameplay on other hosts.

Close old Broomm/emulator instances normally, open the new build, select the account and let idle initial sync run. For GT6 choose **Options → Download Updates and DLC**, or Retry the retained failed job; its verified base download is reused. If the queue is owned elsewhere, quit that copy and select **Downloads → Refresh downloads**. The full UI flow and cleanup/prerequisites are maintained in [README](../README.md#verify-download-limits-cloud-badges-and-emulator-configuration).

The existing Switch cold-initialization boundary and RomM's non-atomic version publication remain unchanged.
