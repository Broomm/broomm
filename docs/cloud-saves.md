# Managed cloud saves

Historical single-file slice, 2026-10-22. The owner subsequently replaced its public save contract: see [BROOMM version history and PS3 ISO support](slotted-saves-and-ps3-iso.md) for the current implementation. The old unslotted asset remains readable for migration and is never overwritten by new sync. The [library/progress follow-up](library-and-progress-followup.md) added DS and Switch save boundaries; counts and release metadata below describe the preceding cloud-save milestone. Product rules are in [PROJECT.md](../PROJECT.md); verification scope and remaining acceptance are in [IMPLEMENTATION.md](../IMPLEMENTATION.md).

## Managed asset and explicit actions

The automatic target is one current-account/current-ROM save with exact `file_name=broomm`, `emulator=Broomm`, and no slot. The filename has no extension; its contents are a ZIP bundle. Account identity comes from authenticated RomM responses, not a display name. Multiple matching assets block synchronization; a renamed asset is no longer followed by its old ID. The save list is inspected to find this identity, but automatic work never downloads, replaces or deletes other save contents.

Home Select/Options adds **Use existing save file**, **Backup savefile** and **Cloud saves**. The first explicitly lists this account's available saves, confirms replacement, imports the selected file into local progress and uploads a freshly sealed `broomm` version. The source is unchanged. The second uploads local progress under a unique temporary backup name, verifies readback and renames it to the requested name. A filename collision never replaces another save. A durable backup checkpoint resumes the original snapshot after a lost response; retries can finish its rename without uploading a duplicate. Only explicit backup retry inspects its temporary asset. A failed backup can leave that temporary asset visible in RomM until retried; it is never an automatic sync target.

New password logins request `assets.write` alongside the existing read scopes. A role that cannot grant it can still sign in for browsing with read scopes. Old refresh tokens retain their original scopes: after a write permission failure, **Sign in to authorize cloud saves** requests the new scope once; an opaque client token must itself grant it. No password is saved and refresh cannot silently upgrade a grant. Read-only accounts retain local progress.

## Session and recovery behavior

The session supervisor holds the existing cross-process SessionLease through prepare, execution, native writer shutdown, snapshot and synchronization. It checks the native writer lock before post-game capture. A PID or parent exit alone is insufficient. Broomm returns visibly on emulator exit, displays progress synchronization and offers **Keep local save and finish later**. The controller/keyboard/pointer controls share the existing Console widgets. Launcher controller input remains available to cloud dialogs before the native process starts and to the finalization screen after it exits; live pairing/gameplay keeps the emulator's SDL/chord input route.

Progress storage is `cloud-saves/<local-server-id>/<local-profile-id>/<rom-id>/`. Immutable snapshots contain a manifest, individual files and a bundle. Native save files remain inside the account's private emulator tree. State tracks the last acknowledged common digest/commit, pending local snapshot, upload intent, interrupted session and conflict copies. Restore snapshots the old files, publishes a journal, replaces only validated game files, verifies their contents, publishes the next state, then removes the journal. Recovery rolls the recorded restore forward; an unexpected file hash stops it rather than overwriting an unrecognized writer. Missing previously recorded ordinary saves are damaged recovery, not a fresh empty save. An explicit existing-save import can repair them.

Before connected play, local/remote/common digests determine upload, pull, equality or conflict. Both conflict versions remain local until a choice succeeds. A failed upload remains pending; readback must confirm the uploaded digest and commit before acknowledging it. Lost upload replies are reconciled by content without creating another managed file. A crashed session requires review before uploading its possibly incomplete progress. An unresolved conflict blocks the next launch until chosen or cancelled.

Every 45 seconds while idle, one pending game for the active server/profile can retry from its immutable snapshot, including after ROM or emulator uninstall. Retry does not restore native files, enumerate another account or need an installed ROM. Account switching and launching cancel and drain that work first. Unchanged problems are deduplicated. Conflicts require the explicit Cloud saves action; reinstall an uninstalled game to reach its Options. Confirmed versions retain the ten newest local recovery copies plus current/pinned interrupted-backup copies; unsynchronized/conflicted versions are not pruned. Uninstall preserves this storage and all native progress.

Hashing, compression, archive inspection, native snapshots, integrity verification and restore run in Dart worker isolates. HTTP bodies stream with byte bounds, idle deadlines and cancellation; transfers do not follow redirects. Logs include operation/ROM phases, timings and rate-limited byte updates without credentials or save contents. No dependency or Go helper was added. SDK zlib supplies ZIP deflate; bounded ZIP parsing/writing and streaming SHA-256/MD5/CRC use Dart. The general [`archive` package](https://github.com/brendan-duncan/archive) supports many more formats and adds dependencies; this slice only needs stored/deflated ZIP and deliberately rejects ZIP64, encryption, links and unsafe/colliding paths. Limits: 512 MiB total/transfer, 256 MiB per progress file, 4095 progress files plus the manifest. Windows-portable filenames are required. Readback and process-interruption recovery are checked; power-loss durability on every filesystem is not claimed.

## Native format boundaries

| Adapter | Included ordinary progress | States and limits |
| --- | --- | --- |
| RetroArch/Snes9x | Current unpacked ROM's `.srm` in the tested `saves/Snes9x` folder; filenames translated to a portable logical name | Matching ROM's states in Snes9x's state directory; only a verified SNES core; legacy root saves/packed-ROM naming need reconciliation/validation |
| Dolphin/GameCube | GCI folder cards A/B, with each GCI's six-byte game/maker ID matching the actual disc header | Game-ID-prefixed state files; shared raw memory cards are not uploaded |
| Dolphin/Wii | Disc title's `Wii/title/00010000/<title>/data` only | Game-ID-prefixed states; NAND identities, SYSCONF, firmware and other titles excluded |
| Azahar | Base title's `data` including metadata, plus extdata identified from its decrypted NCCH extended header | Title-prefixed `.cst`; extended multi-title extdata access is gated rather than guessed |
| RPCS3 | Current PARAM.SFO title-ID-prefixed savedata folders for the private user | No supported states; games using a different savedata prefix need a verified mapping |
| melonDS | ROM-header game-code/revision-scoped raw `.sav`, normalized to `save/game.sav` | Same-ROM states in build/host-specific groups; DSV conversion is outside this adapter |
| Ryubing | Current program/account's committed account-save and matching device-save contents, verified against the native index and ExtraData | Native cold initialization is supervised before restore; index, working data and console identities are excluded; no supported states |

ISO and RVZ/WIA Dolphin headers, decrypted NCSD/NCCH 3DS files and extracted PS3 PARAM.SFO provide game identities. WBFS/CISO and encrypted 3DS headers are not cloud-ready formats in this slice. Other native hosts and Android external-app save access retain their platform-specific requirements; a Dart implementation or macOS build does not establish native access there.

One managed bundle can keep multiple state groups keyed by emulator executable, verified core build when applicable, and host. Only a matching local group is applied. Native state provenance records hashes before play and admits newly written/changed states only after that controlled session stops; states explicitly restored from a matching bundle also acquire known provenance. An unchanged legacy file is never relabelled as the current build, including after a core update. Automatic pulls leave unverified native states untouched and retain any colliding cloud state inside the bundle instead of overwriting or deleting either version. An explicit **Use existing save file** confirmation can apply that remote state. Other build groups survive ordinary save changes on another device. RPCS3/Ryubing states are not claimed. A matching key is a compatibility guard, not proof that a state loads or that a game's patch level matches; cross-device gameplay acceptance is still required.

Explicit existing-save import accepts a matching Broomm backup, a raw SNES SRAM file, an ordinary raw melonDS `.sav`, a matching GameCube GCI, or a bounded ZIP of the supported emulator's complete game-save directory. Azahar ZIP imports need `00000001.metadata` and `00000001/`, optionally inside `data/`. A lone inner directory or raw console `.sav` is not silently treated as an emulator export. Unknown binary/conversion formats fail without replacing the native save. Update/DLC content, emulator settings, keys, console identities, caches and other games are never progress entries.

## RomM 5.4 contract and concurrency limit

Pinned primary sources: [save endpoints](https://github.com/rommapp/romm/blob/5.4.0/backend/endpoints/saves.py), [asset storage/rename](https://github.com/rommapp/romm/blob/5.4.0/backend/handler/asset_store.py), [filesystem asset hashing](https://github.com/rommapp/romm/blob/5.4.0/backend/handler/filesystem/assets_handler.py), [filesystem rename](https://github.com/rommapp/romm/blob/5.4.0/backend/handler/filesystem/base_handler.py), [Dolphin RVZ format](https://github.com/dolphin-emu/dolphin/blob/2609/docs/WiaAndRvz.md), [Azahar extdata metadata](https://github.com/azahar-emu/azahar/blob/2123.2/src/core/file_sys/ncch_container.cpp), and [Azahar state filenames](https://github.com/azahar-emu/azahar/blob/2123.2/src/core/savestate.cpp). Research copies remain in the ignored `.tool-cache/research/cloud-saves/` folder. Validate paths against those retrieved copies before changing contracts.

POST uses multipart `saveFile`, `emulator=Broomm`, `overwrite=false`, `autocleanup=false`; PUT replaces the verified managed ID. No slot/device negotiation is used: slot uploads create timestamped versions, conflicting with the requested single-file rule. GET content uses `optimistic=false`. RomM's content hash is MD5 for raw bytes or MD5 of sorted `entry-name:entry-MD5` lines for ZIP entries. Broomm separately verifies SHA-256 inventories and uses semantic progress digests independent of ZIP timestamps/compression.

RomM 5.4 PUT has **no atomic expected-hash guard**. `content_hash` is bookkeeping, not compare-and-swap. Broomm downloads/rechecks before upload and confirms readback afterward. Causal commit/ancestor IDs detect a later competing Broomm write even when the local device had already acknowledged its own upload; both devices' recovery copies survive until resolution. There remains a server-side race with simultaneous writers, especially external clients without Broomm lineage. Do not claim lossless concurrent writes or manufacture hidden remote lock/backup files. A server-side conditional-write API is needed to eliminate that race. Backup rename uses the server's collision refusal; its upstream filesystem fallback on hosts lacking hard links has weaker cross-worker guarantees and must not be presented as universal CAS.
